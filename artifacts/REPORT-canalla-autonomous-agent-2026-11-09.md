## 1. Что было неправильно на исходном скриншоте

Один экран одновременно утверждал пять разных вещей об одной задаче:

- «Ожидаем первый ответ модели» и «Модель обрабатывает запрос… 680 с» — от композера;
- «Working» — от поля задачи;
- «3/3 steps» — от счётчика плана;
- «Завершено» — от свёрнутой группы инструментов;
- «Web: 1 Search / 0 Fetch» — от подсчёта запусков инструментов.

Пользователь не мог понять, работает ли агент, закончил ли он или ждёт. Ни один из этих
индикаторов не был ложью по отдельности — ложью была их совокупность, потому что они
описывали разные уровни (транспорт, шаг плана, семейство инструментов, задачу) и выглядели
как один статус.

## 2. Точные причины противоречивых статусов

1. **Не было одного авторитета.** `TaskPanel` рендерил `task.message` (общий «Working» для
   PLANNING/RESEARCHING/EXECUTING/VERIFYING), счётчик шагов и `completion_summary`. Композер
   независимо выводил свой таймер потока. SSE-поток живёт всю задачу, поэтому «Модель
   обрабатывает запрос… 680 с» и «3/3 steps» были правдой одновременно.
2. **Счётчик шагов читался как результат.** `done / total steps` стоял рядом со статусом и
   воспринимался как процент завершения задачи. План может быть выполнен, пока идёт
   обязательная проверка.
3. **Метка семейства была без области действия.** `groupStatus()` возвращал строку
   «Завершено», когда все запуски *семейства* завершились; в свёрнутом заголовке это
   читалось как «задача завершена».
4. **`message` не различал ожидания.** `status_message()` отдавал «Working» для шести
   состояний и не сообщал, чего именно ждёт задача (модель, разрешение, устройство, ресурс).
5. **Не было времени последней активности.** UI не мог показать «последняя активность N
   секунд назад» и не мог отличить долгую генерацию от зависания.

## 3. Где задавался лимит страниц и почему он сработал

Три независимые причины, все подтверждены тестами:

1. **Несогласованные бюджеты.** В `chat_stream.py` задача получала
   `max_fetch = settings.tools_task_max_fetch` (12), но `max_pages = settings.tools_max_pages`
   (по умолчанию **10**, потолок 20). Один fetch может запросить до 3 URL, поэтому законные
   12 загрузок упирались в безымянный лимит 10 страниц первыми. Пользователю показывали
   `page_limit`, хотя счётчик Fetch ещё не был исчерпан.
2. **Tor списывал бюджет прямой сети.** В `ToolLimits.consume` строка `self.pages += pages`
   выполнялась для любого инструмента с `urls`, включая `tor_fetch`. Tor-загрузка увеличивала
   и `tor_pages`, и общий `pages`. Отсюда буквально наблюдаемая пара: «Web: 0 Fetch» и
   «Достигнут лимит загруженных страниц» — страницы израсходовало другое семейство.
3. **Сообщение не содержало чисел.** `ToolError("page_limit")` — только код. UI не знал ни
   фактического лимита, ни счётчиков, поэтому не мог объяснить, что именно кончилось.

Дополнительно: `web_fetch` не запускался автоматически для computer-задач
(`skip_cheap_web`), поэтому модель могла сделать только `web_search`, а страницы так и не
были прочитаны. Пользователь получал сниппеты, поданные как изученные статьи.

## 4. Как теперь считаются Search, Fetch, Files, Tools

**Search / Fetch.** Считаются завершённые запуски инструментов (`ToolRun`) по имени, раздельно
для прямой сети и Tor, и раздельно по происхождению: `model`, `server_policy`, `other`.
Контроллер больше не выдаёт свои действия за решения модели.

**Страницы.** Появился собственный бюджет задачи: `tools_task_max_pages` (36) и
`tools_task_hard_pages` (60), то есть он согласован с `tools_task_max_fetch` (12 × 3 URL).
Прямые загрузки списывают только `pages`; Tor — только `tor_pages`.

**Файлы / инструменты.** `tools_used / tool_budget` и `files_changed / file_change_budget`
берутся из персистентной строки задачи и отдаются в `budgets`; UI больше не угадывает их из
локального состояния.

**Найдено / открыто / не удалось.** Каждый сетевой запуск пишет в `result_metadata.web`
`{requested, opened, failed}`. Задача агрегирует их в `web.pages_requested / pages_opened /
pages_failed`. Если поиск был, а страниц открыто 0, интерфейс прямо пишет «источники найдены,
страницы не прочитаны».

**Исчерпанный лимит.** `ToolLimits.snapshot()` сохраняется в факты задачи как `last_limit`, а
панель показывает реальные числа: «Лимит страниц: 10 из 10 страниц · 3 из 12 загрузок ·
1 из 5 поисков». Никаких безымянных «лимит достигнут».

## 5. Как отображается текущая активность

Под лентой сообщений (над композером) — одна компактная строка:

> **Работает** · Run pytest · 3/3 · последняя активность только что · источники найдены, страницы не прочитаны — `04:32`

- Статус, тон и текст приходят из одного backend-поля `phase`;
- `last_progress_at` вычисляется как максимум из `updated_at` задачи и времени последнего
  события журнала, поэтому после перезапуска UI показывает то же самое, а не локальный таймер;
- при ожидании модель/ресурс — «Ожидается ответ модели · 11 мин назад · llm_timeout»;
- при простое дольше порога фазы — «нет событий 20 мин назад» (тон ошибки);
- «Подробности» раскрывают бюджеты, счётчики web, лимит, план и таймлайн событий с точным
  временем из `task_events`.

Композер во время активной задачи больше не показывает собственный «Модель обрабатывает
запрос…», а плейсхолдер пустого ответа говорит «Canalla LLM выполняет задачу — итог появится
здесь».

## 6. Как пользователь определяет, когда задача закончена

Только по `phase`. `completed` выставляется исключительно когда задача закрыта контроллером
(`conclude`) и `final_review` пройден. Счётчик шагов на это не влияет:

- 3/3 шагов при идущей проверке → `verifying` («Работает»);
- завершённое семейство инструментов → «веб-инструменты завершены», не «задача завершена»;
- FAILED с реально выполненной работой → `partial` («Не удалось завершить · причина ·
  выполнено N из M»);
- FAILED без единого выполненного шага → `failed` (пропущенные шаги не считаются работой);
- остановка пользователем → `cancelled` («Остановлено · остановлено вами»).

## 7. Как работает Web → Research

1. Запрос классифицируется (`classify_web`); при необходимости — серверный поиск.
2. Найденные источники дедуплицируются каноническим URL.
3. Если поиск был, а страницы не читались, контроллер выполняет **один ограниченный бесплатный
   `web_fetch`** собранных источников (≤3 URL) и помечает его `server_policy`. Раньше для
   computer-задач этот шаг пропускался, и страницы оставались непрочитанными.
4. Текст страниц попадает в `context.sources`, привязывается к сообщению
   (`web_source_snapshots`) и доступен в панели источников с датой публикации.
5. Если провайдер не вернул текст, запуск честно падает типизированно (`fetch_failed`), а не
   показывает зелёное «Завершено» над пустым результатом.

Чего нет: «использовано в ответе» пока не вычисляется как отдельный счётчик — источники
показываются с метками, но связь «метка → абзац ответа» не агрегируется.

## 8. Как работает Research → Build → Run → Verify

Цепочка существует и покрыта тестами (не изменялась в этом цикле):

- `default_plan` строит проверяемые шаги; `LocalTaskController` ведёт их;
- файлы пишутся через `write_file`/`patch_file` с проверкой SHA и `after_sha256`;
- `run_python`/`run_process` дают реальный stdout/stderr и exit code;
- `verify` требует пройденных тестов; `verification_stale` не даёт закрыть задачу;
- `final_review` — единственный источник COMPLETED; при провале задача становится
  FAILED/PARTIAL с причиной.

Тест `test_mock_e2e_fix_and_verify` проходит полный цикл «прочитать → исправить → прогнать
pytest → подтвердить» на настоящих файлах во временном каталоге.

## 9. Какие действия Canalla выполняет сама

В рамках подтверждённого режима (Computer `ask`/`trusted`, разрешённый workspace): чтение и
запись файлов, патчи, создание каталогов, запуск Python/процессов, pytest, git status/diff,
поиск и чтение веб-страниц, Tor-маршрут, повторные попытки при типизированных сбоях,
восстановление после обрыва модели. Вне разрешённого scope действие блокируется
(`workspace_scope`) и требует нового подтверждения.

## 10. Как устроена автономность и восстановление

- Состояния задачи — `machine.py` (20 состояний, запрещённые переходы бросают
  `invalid_task_transition`).
- Журнал `task_events` с монотонными метками: два события в одну микросекунду больше не могут
  поменяться местами, поэтому таймлайн восстанавливается детерминированно.
- `last_progress_at`, `idle_seconds`, `stalled` — производные от журнала, а не от таймера
  компонента.
- Перезапуск UI: `GET /tasks/{id}` возвращает `phase`, `completed/remaining`, `limit`, `web` и
  `events`; повторного выполнения завершённых инструментов нет (`completed_digests`, отдельный
  тест).
- Stop/Resume: остановка реально останавливает генерацию и оплачиваемый compute через
  существующую безопасную семантику; Resume не повторяет уже завершённые side effects.

## 11. Режим разрешённого security assessment

**Не реализован в этом цикле.** В коде нет ни scope-контракта для проверок, ни поиска
CVE/advisories, ни отчёта об уязвимости. Существующие границы (`scope.py`,
`computer_mode`, подтверждения) не дают выполнить действие вне разрешённого workspace, но
это не заменяет security-workflow.

Причина: это отдельный продукт-срез (модель scope, источники, safe validation, evidence,
UI), который нельзя честно закрыть «наполовину». Платные проверки для него не запускались.

git push, критические операции. `computer_mode=ask` сохранён — значение в базе не менялось.

## 18. Что реализовано, что PARTIAL / BLOCKED

**Реализовано и проверено**

- Честные статусы: `partial`, `cancelled`, `waiting_resource`, `waiting_model`,
  `waiting_permission`, `stalled`, `idle_seconds`, `last_progress_at`.
- Компактная строка статуса с раскрываемыми деталями и таймлайном из журнала.
- Композер и плейсхолдер ответа больше не спорят с задачей.
- Область действия у меток семейств инструментов.
- Согласованные бюджеты страниц; Tor больше не тратит бюджет прямой сети.

- Один ограниченный бесплатный fetch, когда модель только искала.
- Монотонный журнал событий.

**PARTIAL**

- «Использовано в ответе» как отдельный счётчик источников — не агрегируется.
- Сохранение и отображение дат публикации есть в источниках, но не выводится как отдельная
  колонка в панели задачи.

**BLOCKED**

- Платные live-гейты (D2 LIVE, LA LIVE, T3 LIVE, T4 LIVE) — запуск Pod запрещён условиями
  этого этапа.
- Установленный UI smoke для новой панели — требует нового NSIS-инсталлятора; сборка
  `build-desktop.ps1` блокируется upstream-архивом Tor (`tor-expert-bundle-…-15.0.25.tar.gz`
  отдаёт 306 байт), независимо от изменений этого цикла.

**НЕ РЕАЛИЗОВАНО**

## 19. Нужны ли платные Qwen-тесты
