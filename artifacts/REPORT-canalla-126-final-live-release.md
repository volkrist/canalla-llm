### 2.2 Дефекты публикации, найденные и устранены сегодня

Публикация застряла на шаге `14_manifest`. Разбор дал четыре независимые причины — все в инструментарии релиза, ни одна не в продукте.

1. **Имя файла на Gateway не совпадало с подписанным.** Шаг 12 копировал инсталлятор под именем, которое GitHub санирует (точки вместо пробелов), а manifest собирал URL из подписанного имени (`Canalla LLM_…` с пробелом). Публичный URL отдавал 404. Теперь Gateway-копия использует подписанное имя, а «санитизированное» осталось только для GitHub (`GATEWAY_ASSETS`).
2. **Cloudflare закэшировал этот 404 на 4 часа** (`cf-cache-status: HIT`, `Age: 179`, `max-age=14400`). Даже после исправления имени чистый URL оставался мёртвым. Каждый релиз теперь получает собственный cache-buster `?v=1.2.6`; подпись привязана к имени файла, а не к query, поэтому привязка не нарушается.
3. **Шаг 14 не мог увидеть собственную публикацию.** `_http` **заменял** заголовки, а не дополнял их: запрос с одним `Cache-Control` уходил без `User-Agent`, Cloudflare отвечал `403 error code 1010`, проба возвращала «манифеста нет», а шаг рапортовал «Gateway всё ещё отдаёт предыдущую версию». Заголовки теперь объединяются с дефолтным UA.
4. **Шаг 15 падал на Windows.** Он передавал *содержимое* подписи там, где скрипт читал *путь* (`OSError: [Errno 22]`). Скрипт принимает и содержимое, и путь. Раньше это не всплывало, потому что шаг 15 ни разу не запускался — его всегда отсекал шаг 14.

Дополнительно: self-test релиза больше не пишет свои фиктивные шаги (`01_a`, `02_b`) в боевой `release-progress.json`.
