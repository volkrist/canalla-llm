1. Резюме

Задание выполнено в той части, которую можно доказать на этой машине, и там, где среда не позволила — это зафиксировано честно, а не замаскировано.

Подтверждено:

  • Ubuntu runtime acceptance — PASS 10/10: собранный из этого дерева Linux-sidecar отвечает /health с полностью пустым PATH, сообщает версию 1.2.7; встроенный Tor 0.4.9.16 реально поднимает SOCKS5h-цепь, переживает убийство демона и восстанавливается с новым доказательством, после остановки не оставляет процессов.
  • Обновление 1.2.6 → 1.2.7 на реальных данных 1.2.6: sidecar 1.2.7 мигрировал базу 0016 → 0017, создал проверенный pre-upgrade backup, пользователь и чат сохранились.
  • Откат: 1.2.6 на базе 0017 больше не падает с CommandError, а типизированно отказывается — exit 16, database_ahead, база не тронута, лишний backup не создаётся. Дефект найден этой приёмкой и исправлен.
  • Финальный артефакт: собран заново, updater-подпись production-ключом, полный релизный гейт candidate — 22/22 PASS.
  • Production 1.2.6 восстановлена байт-в-байт после инцидента с установщиком (раздел 7).

Не подтверждено (и почему):

  • Чистая Windows VM: VirtualBox и бесплатный ISO есть, VM создана, Windows Setup загружается, но unattended-фаза откатывается на ~11%. Ограничение среды, не продукта (раздел 4).
  • Удаление программы на пользовательской установке не выполнялось: оно удалило бы рабочее приложение. Поведение неизменно с 1.0.0 — uninstaller удаляет только каталог программы.
  • LEVEL 6/7 остаются BLOCKED_BY_LIVE_BUDGET / NOT_TESTED (раздел 11).

4. Чистая Windows VM: что сделано и где остановилось

Создана VM Canalla-127-Acceptance (Windows11_64, EFI, TPM 2.0, 4 GB RAM, 2 CPU, диск 40 GB на D:, общая папка, Guest Additions). Путь установки прошёл несколько реальных препятствий, каждое исправлено:

  1. ISO не подключался: у SATA-контроллера было 2 порта, и aux-образ занял единственный свободный. Исправлено: 4 порта + явное подключение ISO.
  2. VirtualBox обернул ISO в aux-образ и потерял El Torito (cBootCatEntries: none) — VM уходила в EFI shell. Исправлено: загрузка с оригинального ISO.
  3. ISO ждёт нажатия клавиши («Press any key to boot from CD or DVD»), headless-загрузка без клавиатуры уходила в Boot Manager. Исправлено: подача скан-кодов в нужное окно.
  4. Файл ответов на дискете не подхватился — Setup показал выбор языка. Исправлено: отдельный маленький ISO с autounattend.xml как второй оптический носитель.
  5. Установка доходит до «Installing Windows 11 — 11%» и после перезагрузки машина не находит загрузочный диск (BdsDxe: No bootable option), VDI остаётся ~1.1 GB. Повторные попытки (включая загрузку с DVD) не продвигают фазу apply.

Итог: чистая VM создана и Windows Setup в ней запускается, но unattended-установка в этой среде не завершается. Это ограничение среды (Hyper-V + VirtualBox 7.2, 8 GB RAM), а не дефект продукта. Прямое следствие: матрицу установки проверяли на реальной установке с проверенным снимком и восстановлением (раздел 7), а чистая VM остаётся предусловием публикации.

6. Установка, обновление, сохранение данных

6.1. Что произошло фактически

План был установить 1.2.7 в изолированный каталог через /S /D=<dir>, предварительно убрав ключ деинсталляции, чтобы NSIS видел «чистую машину». Установщик проигнорировал /D и обновил реальную установку %LOCALAPPDATA%\Programs\Canalla LLM — это и есть настоящее обновление 1.2.6 → 1.2.7, но оно затронуло пользовательскую установку.

Действия сразу после обнаружения:

  1. Payload 1.2.7 сохранён в D:\canalla-vm\host-accept\payload127 (версия 1.2.7, exe d1ec80fd…).
  2. Production восстановлена из снимка, сделанного до установки: robocopy /MIR из D:\canalla-vm\prod-snapshot\program.
  3. Проверка восстановления: exe 21b50e462156b9f109303623e4c67225d4e44daad981d8f439a83d16c8cafaf1 — совпадает с исходным, 1278 файлов, ProductVersion 1.2.6.
  4. Ключ деинсталляции возвращён на DisplayVersion 1.2.6 и тот же InstallLocation.
  5. HKCU\Software\Canalla LLM пересоздан (в нём были только артефакты тестов autostart-test; приложение там настроек не хранит).
  6. Ярлык в меню «Пуск» восстановлен из снимка.

6.3. Ограничение, найденное по ходу

Установка «рядом» невозможна: NSIS игнорирует /D и всегда ставит в %LOCALAPPDATA%\Programs\Canalla LLM, заменяя установленную сборку. Это зафиксировано в release notes; данные при этом не затрагиваются.

7. Откат: найден и исправлен реальный дефект

Откат на 1.2.6 после миграции 1.2.7 ранее заканчивался так:

alembic.runtime.migration ... upgrade 0016 -> 0017
alex.runtime migration_failed CommandError

То есть 1.2.6 видел ревизию 0017, считал её «ожидающей миграцией», пытался выполнить upgrade head и падал с CommandError; backend не стартовал, причина не названа.

Исправление (apps/backend/app/runtime_entry.py):

  • migration_state() различает «эта сборка позади базы» и «есть работа для миграции»;
  • при базе новее сборки — exit 16, ALEX_RUNTIME_ERROR database_ahead current=… build=…, запись runtime/migration.json с result: refused_database_ahead;
  • база и её backup не трогаются, лишний pre-upgrade backup не создаётся.

Регрессионный тест: tests/test_upgrade.py::test_a_database_from_a_newer_build_is_refused_not_migrated (подменяет ревизию на будущую и проверяет код 16, запись, отсутствие backup и сохранность данных). Весь файл: 11 passed.
