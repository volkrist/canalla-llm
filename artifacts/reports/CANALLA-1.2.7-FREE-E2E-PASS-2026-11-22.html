A. Первопричина потери tests_passed (доказана, а не предположена)

verification.tests становится passed только через run_python с -m pytest и exit_code=0; любой последующий write_file сбрасывает флаг в stale.

После рестарта fake-модель, ориентируясь на счётчик вызовов планировщика, «доезжала» на шаг назад и повторяла запись уже после pytest — продукт корректно помечал проверку устаревшей. Счётчик дрейфовал на один вызов, потому что планировщик вызывается не только на каждый tool call.

Исправление: fake-модель принимает решение по транскрипту. Как только в разговоре есть собственный вывод pytest (test session starts), новые записи не предлагаются — остаётся только независимая проверка. Это не ручная запись passed в БД: флаг по-прежнему ставит продукт по реальному exit_code pytest.

C. Что проверяет тест (не фиктивность)

  • Настоящий pytest исполняется на хосте и его exit_code управляет tests_passed.
  • test_smoke.py проверяет поведение (add(2,3) == 5), а не существование файла.
  • Kill происходит только после фиксации pytest, при статусе VERIFYING.
  • После рестарта новое действие (verify_result) исполняется реально, task_id сохраняется.
  • COMPLETED ровно одно.
  • Любая последующая запись сделала бы tests снова stale — механизм не отключён.
