A. Что установлено по схемам (не по предположению)

  • verification.tests = "passed" ставится только в LocalTaskController._capture_facts: нужен run_python/run_process/run_powershell, чей argv содержит -m pytest (или purpose упоминает pytest), и exit_code == 0; тогда tests_passed = True, verification_stale = False.
  • Любой последующий WRITE_TOOLS сбрасывает tests_passed = False и verification_stale = True.
  • final_review() для кодирующего запроса требует verification.tests == "passed".
  • Схема run_python: argv, cwd, timeout_seconds, purpose, wait.

B. Что реализовано

fake_llm.py — детерминированный сценарий:

  1. write_file app.py (def add(a, b));
  2. write_file test_smoke.py (реальная проверка add(2,3) == 5);
  3. write_file part3.txt, write_file final.txt;
  4. run_python {argv:["-m","pytest","-q"], cwd:<workspace>, purpose:"verify project tests"};
  5. verify_result по абсолютным путям workspace;
  6. завершение.

Планировщик отвечает с задержкой 1.2 с, чтобы финальная проверка не успевала проскочить до kill.

free_resume_e2e.py — прерывание по факту завершённого pytest (прямой read-only запрос к изолированной SQLite, опрос 0.2 с), а не по счётчику запусков.

D. Оставшийся дефект

После рестарта tests возвращается в stale, хотя pytest уже завершился успешно. stale выставляется только записью (WRITE_TOOLS), значит после рестарта произошёл write, либо tests_passed не был зафиксирован в checkpoint и был потерян при восстановлении контекста.

Следующий шаг диагностики (точный): сравнить facts["tests_passed"] и row.checkpoint до kill и после рестарта; проверить, не входит ли tests_passed/verification_stale в сохраняемый checkpoint. Если флаг не переживает рестарт — сохранять его в checkpoint вместе с digests_completed (это штатное место для восстановимого состояния, а не ручная запись passed в БД).
