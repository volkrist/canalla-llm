E. Найденный дефект продукта (не теста)

Цепочка событий после resume: RESUMED → RESUMED → MODEL_RESPONSE → FAILED. Поток POST /tasks/{id}/resume уходит сразу в генерацию ответа и не выполняет планировочный раунд, поэтому модель не может запросить новый инструмент (в сценарии — verify_result). Контроллер при этом корректно отказывается объявлять задачу выполненной: файлы изменены, независимой проверки нет (last_error = verification_required).

Иными словами: durable resume не позволяет продолжить работу инструментом после перезапуска, если прерывание произошло между изменениями и верификацией. Это именно тот класс дефекта, который обязан ловить LEVEL 7.

F. Исправленные ошибки этой сессии

  1. Fake-сервер не доходил до backend — добавлен LLM_CONNECTION_MODE=static.
  2. Задача не становилась автономной — промпт приведён к автономному сценарию.
  3. WAITING_DEVICE — добавлены ALEX_DEVICE_DIR, ALEX_DEVICE_CREDENTIAL_TARGET, запуск host loop.
  4. Host умирал после kill backend — E2E перезапускает host вместе с backend B.
  5. Сценарий fake-модели «плыл» от лишнего планировочного запроса — переход на состояние из транскрипта + флаг verification_asked.
  6. Повреждённая git-ссылка ветки после аварийной записи — восстановлена update-ref на существующий коммит, история не потеряна, push выполнен.
