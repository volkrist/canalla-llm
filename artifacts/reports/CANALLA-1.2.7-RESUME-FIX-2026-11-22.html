A. Цель блока

Устранить дефект, из-за которого resumed-задача не получала планировочного раунда, довести free_resume_e2e.py до verify_result → один COMPLETED → verifier PASS.

B. Что исправлено

B.1. Пропуск планировщика — исправлено (проверено прогоном)

Симптом: RESUMED → RESUMED → MODEL_RESPONSE → FAILED, last_error = verification_required, COMPLETED = 0, хотя файлы созданы и задача продолжалась.

Причина (в коде, не в отчёте): ToolOrchestrator._goal_satisfied() возвращал True по фактам файлов. В prepare() это выставляет skip_planner = True, цикл планирования не запускается, verify_result моделью не запрашивается. Контроллер затем корректно отказывает в завершении.

Исправление (apps/backend/app/tools/orchestrator.py): задача, изменившая файлы, считается «goal satisfied» только если verification.evidence_ok == true или verification.tests == "passed".

Подтверждение эффекта: после исправления в прогоне 271f0ded… resumed-фаза выполнила на 2 инструмента больше (completed_runs 3 → 5), и среди них — реальный verify_result.

B.2. Fake inference: абсолютные пути

fake_llm.py теперь собирает цели проверки из абсолютных путей в транскрипте (рекурсивный обход запроса), а не из относительных имён, которые резолвились от cwd backend.

D. Открытый дефект (блокирующий PASS)

Из tool ledger последнего прогона:

verify_result  completed  ok=False
evidence: {'total': 2, 'ok': 0, 'failed': 2,
           'kinds': {'CHECK_REFUSED': {'ok': 0, 'failed': 2}}}

Обе проверки отклонены guard'ом workspace-roots в verify_result (_roots / _inside), поэтому evidence_ok = false, задача завершилась FAILED / verification_required.

Это не дефект сценария: реальные файлы лежат в workspace задачи, но guard на resume-пути их не признаёт. Требуется либо включить context.workspace.primary_root в _roots, либо нормализовать пути перед сравнением (как уже сделано в security_assessment.scope после Linux-гейта).
