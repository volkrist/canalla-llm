C. Что сделано (требование → результат → доказательство)

C.1. Реальный поиск без платного ключа — PASS (LIVE)

Проблема: web_search и web_fetch были привязаны к TinyFish. На установке без ключа модель видела два инструмента, которые умели только отвечать provider_not_configured, и была обязана объяснять пользователю проблему с креdentials вместо ответа на вопрос.

Сделано:

  • apps/backend/app/tools/search/providers.py — четыре адаптера официальных бесплатных API: Wikipedia (MediaWiki), arXiv (Atom), Stack Exchange, GitHub;
  • apps/backend/app/tools/search/chain.py — выбор провайдеров по типу вопроса, параллельный запуск, дедупликация по каноническому URL, чередование источников, типизированные ошибки (rate_limited, timeout, forbidden, …), учёт include_domains / exclude_domains;
  • apps/backend/app/tools/search/provider.py — web_search (платный провайдер, если ключ есть, иначе цепочка) и web_fetch (платный reader или собственный robots-aware клиент продукта);
  • deep_research использует ту же цепочку, поэтому исследование работает без ключа;
  • registry.py: описание инструментов больше не обещает провайдера, которого нет.

Доказательство:

  • offline: tests/test_free_search.py — 17 passed (разбор реальных форматов API через httpx.MockTransport, типизированный rate limit, дедупликация, фильтры, отказ от выдуманных источников, fallback-выбор провайдера);
  • LIVE: tests/test_live_web_smoke.py -m live_web — 5 passed по настоящей сети без ключа; реальные результаты сохранены в artifacts/acceptance-search/free-search-live.json:

C.2. Память проекта через настоящий перезапуск — PASS (механика)

Сделано: apps/backend/tests/helpers/memory_worker.py + tests/test_127_memory_resume.py. Три независимых процесса делят только файл SQLite: один создаёт проект, историю чата и четыре памяти (две проектные, одна закреплённая общая, одна чужого проекта, одна чужого аккаунта) и завершается; второй строит контекст модели после «перезапуска»; третий удаляет запись; четвёртый перезапуск подтверждает удаление.

Проверено: проектные решения попадают в сообщения модели без повторного объяснения пользователя; память чужого проекта и чужого аккаунта не попадает; use_count растёт и сохраняется; при use_memory = false выборка пуста; удаление одной памяти не затрагивает остальные.

Найден и исправлен дефект: _drop_superseded в app/context_builder.py считал два общих слова «тем же фактом», поэтому два решения одного проекта («Alpha uses FastAPI…» и «Alpha tests run with pytest…») молча теряли более старое. Теперь замена требует, чтобы общий словарь составлял не менее половины короткой записи: исправление («Kazan» → «Moscow») по-прежнему заменяет, а другой факт сохраняется.

Доказательство: tests/test_127_memory_resume.py — 4 passed, включая юнит-тест самого правила.

C.4. Матрица recovery — пять контролируемых сбоев — PASS (механика)

apps/backend/tests/test_127_recovery_matrix.py фиксирует каждый сбой отдельной строкой:

Сбой Ожидаемое безопасное состояние

Найден и исправлен дефект: LocalTaskController.finish() добавлял событие завершения даже для уже терминальной задачи. Два пути завершения (tool loop и поток ответа, либо возобновлённый процесс, гоняющийся с погибшим) могли дать два «готово» по одной задаче. Теперь второй вызов возвращается сразу и фиксирует только конфликт как FINISH_IGNORED.

D. Исправленные дефекты

  1. Мёртвые web_search / web_fetch без ключа — заменены на провайдер-независимую цепочку с бесплатными официальными API и собственным reader'ом продукта.
  2. _drop_superseded терял разные факты одного проекта — правило замены переведено с «два общих слова» на отношение общего словаря к короткой записи (≥ 0.5).
  3. Модель видела недоступный провайдер как обычный инструмент — описание инструментов теперь соответствует реальному поведению (платный путь — оптимизация, не условие работы).
  4. Двойное «готово» по одной задаче — finish() больше не добавляет событие завершения терминальной задаче; конфликт фиксируется как FINISH_IGNORED.
  5. Scope проверки безопасности отвергал путь внутри workspace на POSIX — цель нормализовалась, а корень — нет (найдено Linux gate). Теперь нормализуются обе стороны.
  6. Тест test_missing_key_chat_still_completes кодировал старый дефект — ожидал provider_not_configured для отсутствующего платного ключа. Контракт обновлён: бесплатная цепочка запускается, а при недоступности всех бесплатных провайдеров причина — search_unavailable, и чат всё равно завершается.

J. Что осталось и почему

  1. LEVEL 6/7 — нужен один платный LIVE; бюджет исчерпан ($0.358 < минимального окна).
  2. Модель-ведомый research/repair — инфраструктура и живой поиск готовы, но прогон модели требует LIVE.
  3. Платный TinyFish-путь — нужен ключ владельца; бесплатный путь теперь полноценный.
  4. Computer Use сценарий C — UIA и always-ready проверены ранее; повтор с реальной моделью требует LIVE.
  5. Полный updater E2E — нужен опубликованный манифест; публикация не разрешена.
  6. Чистая Windows VM — недоступна бесплатно (VirtualBox на 8 ГБ не завершает установку).

Следующая автоматически выбранная задача: добавить интеграционный тест Computer Use (сценарий C) на изолированном тестовом приложении и подготовить один платный LIVE как единое окно для LEVEL 6/7 (когда бюджет появится).
