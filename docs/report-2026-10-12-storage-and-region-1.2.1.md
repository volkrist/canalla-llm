| Точка монтирования | `/workspace`; при наличии network volume — автоматически `/workspace-global`. Максимум **один global + один network** на Pod. |

## 3. Проверенные ограничения llama.cpp/GGUF и поддержка в коде

### Global Volume и GGUF
Ничто в документации не утверждает, что `mmap` **не работает**; документация прямо снимает
POSIX-гарантии, на которые `mmap` опирается. До живого теста продукт **не может** опираться на
глобальный том для чтения GGUF. Плохой путь чтения проваливается **на загрузке модели**, то есть
после начала списания денег — это то, что нельзя допускать.

### Поддержка обоих видов хранилища в коде (Block C) — PASS

Абстракция существует и покрыта тестами:

* `apps/backend/app/compute/candidates.py`: `Placement.storage_type ∈ {regional_network_volume,
  global_volume}`; `pins_datacenter` — региональный том **закрепляет** ДЦ, глобальный — **нет**;
  неизвестный вид ведёт себя как закреплённый (**fail closed**).
* `_placement_centers()`: региональный placement предлагает **только свой** ДЦ (и только при
  броснируемом стоке); глобальный — каждый ДЦ, который каталог сам считает доступным, «домашний»
  первым. `dataCenterIds` — список, планировщик вправе выбрать.
* `create_verdict()`: однозначный отказ (400/403/404/409/422) → следующий кандидат; **ambigious**
  (timeout/5xx/malformed) → `create_unknown`, **никогда** слепого повторного create.
* `parse_placements()` из `RUNPOD_DATACENTERS` создаёт **только** региональные placement'ы —
  то есть конфигурацией ввести непроверенный глобальный том **невозможно** (безопасно по
  построению).
* `RUNPOD_REPLICAS` пишет `storage_type: regional_network_volume` (`scripts/finish-secondary-replica.py`).

Проверенные живьём результаты (offline, без GPU):

| Набор | Команда | Результат |
|---|---|---|
| Gateway durable wait | `pytest apps/gateway/tests/test_capacity_wait.py` | **13 passed** |
| Backend аллокация + demand | `pytest apps/backend/tests/test_allocation_candidates.py tests/test_cloud_demand.py` | **111 passed** |

`apps/gateway/tests/test_capacity_wait.py` покрывает ровно требуемые сценарии: ожидание живо через
3 виртуальных часа; появившаяся GPU бронируется **ровно один раз** и подключается к ожидающему
чату; поллинг чаще backoff не бьёт по провайдеру; отмена останавливает поиск и запрещает Pod;
цена выше лимита оставляет ожидание с `price_limit`; исчерпан бюджет не создаёт Pod; **рестарт
Gateway сохраняет ожидание и всё равно берёт один Pod**.

## 5. Сравнение регионов/GPU — BLOCKED без живого каталога

Живое read-only чтение каталога требует `RUNPOD_API_KEY`. На этом ПК (недоверенная Windows с
незакрытым `Trojan:Win32/LummaStealer.DO!MTB`, `DidThreatExecute=True`) **production-ключ размещать
нельзя**. Поэтому ранжирование регионов здесь **BLOCKED** и должно быть выполнено владельцем на
Gateway-хосте или в CI.

Существующий инструмент (reuse, не дублировать): `scripts/region-inventory.py` — read-only, печатает
тома, предложения GPU по каждому ДЦ и совместимые (≥ 48 GB) офферы с доступностью; `--history FILE`
добавляет таймстамп в JSONL. **Один снимок — не рейтинг надёжности**: нужна серия во времени.

Последняя записанная живая точка (24–25.09.2026): **только L40S 48 GB $1.09/ч в `US-TX-3`**, сток
`LOW`; A40 48 GB $0.49 внутри потолка, но сток был `NONE`. **Истории доступности по часам недели в
репозитории НЕТ** — её надо собрать read-only или честно признать недостаточной. Вероятность
доступности не выдумывается.

Кандидаты ≥ 48 GB для сравнения (проверяемы тем же инструментом): A40 48 GB, RTX A6000 48 GB,
L40 48 GB, L40S 48 GB, RTX 6000 Ada 48 GB. `CA-MTL-1` / `EU-SE-1` по одному октябрьскому снимку
**нельзя** считать гарантированно доступными.

Предварительно замороженный резервный ДЦ (из решения 25.09.2026, требует **одного** read-only
подтверждения): **`US-KS-2`** — тот же регион комплаенса/класса задержки, присутствует в S3-списке
провайдера (дёшево реплицировать), тот же размер/класс.
