## A. UI-БАГ: КОРНЕВАЯ ПРИЧИНА И ФИКС — ✅ ИСПРАВЛЕНО

### Что видел оператор и что было на самом деле

| Показание | Факт |
|---|---|
| «GPU selection = Вручную» | В БД `selection = automatic`. Значит **UI-состояние разошлось с хранимым** |
| «Exact GPU = NVIDIA L40S» | Это **placeholder пустого поля**, а не значение: `gpu_id` был `null` |
| Красное «Для автоподключения выберите точный GPU…» | Текст существует **только** в `apps/backend/app/compute/schemas.py:39` — это 422 от backend'а |

### Три причины, все в `ComputePanel.tsx`

1. **Хардкод в дефолтах** (строка 118): `gpu_id: "NVIDIA L40S"`. Имя карты засевалось в форму, а затем
   могло уехать в PUT.
2. **Placeholder вместо значения** (строка 579): `placeholder="NVIDIA L40S"` в поле, чьё значение
   `preferences.gpu_id || ""`. Пустое поле **выглядело заполненным**.
3. **Переключение режима ничего не чистило**: `selection` менялся, `gpu_id` оставался. А `search()`
   принудительно ставит `auto_connect: true`, и backend по правилу
   `auto_connect && selection=="manual" && !gpu_id` отвечает 422 → красный баннер. В режиме
   `automatic` с `gpu_id=null` это правило **не срабатывает никогда** — значит в момент ошибки UI был
   именно в «Вручную».

Итого: оператор переключился на «Вручную» (экспериментируя), увидел похожее на значение имя карты,
нажал «Запустить AI» — и получил отказ. В БД осталась последняя **успешная** запись:
`automatic`, `gpu_id: null`, `auto_connect: true` (последнее — след успешного `search()`).

### Что сделано

- `gpu_id` по умолчанию — `null`; в форме **нет ни одного имени GPU**.
- Поля точной карты **не существует в автоматическом режиме**; оно появляется только в ручном и
  заполняется **выбором из живого каталога** (`GET /compute/options`) — обычный пользователь никогда
  не вводит имя карты руками.
- Переключение в «Автоматически» **сбрасывает** пин; обе записи (`/compute/preferences` и
  `/compute/search`) идут через один wire-формат, поэтому скрытый пин не может уехать.
- Единственное нерабочее состояние объясняется **до** отправки, а не 422-м после.
- `automatic` + `gpu_id = null` — **валидное и предпочтительное** состояние; тест прямо это утверждает.

Правила вынесены в `src/lib/compute-policy.ts` (как `ai-connection.ts`, `installer-policy.ts`), чтобы
панель и тесты не могли разойтись.

## B. ЖИВОЙ SHARED AUTO-ENSURE — КОРНЕВАЯ ПРИЧИНА

Разбор по фактам из лога и БД (не по догадкам):

| Факт | Источник |
|---|---|
| Запрос ушёл: `POST /chats/8765161b…/stream 200` | `backend.log` 10:21:28 |
| `POST gateway/compute/ensure` **200** через 4 с | `backend.log` 10:21:32 |
| Ещё два ensure с шагом **ровно 30 с** | 10:22:03, 10:22:33 |
| `GET gateway/v1/models` → **409** каждые ~10 с, 11 минут | `backend.log` 10:21:34 … 10:32:19 |
| Строки: `user` complete + `assistant` **error, пусто** | `messages` |
| **0 генераций**, 0 новых сессий compute | `generation_usage`, `compute_sessions` |
| Gateway: `state=offline error=gpu_unavailable session=- create_attempts=0` | CLI на VPS |

### Что это значит

`SharedDemand.wait_until_ready` (`app/cloud/demand.py:260`) устроена так:

- **один** `self.ensure()` перед циклом;
- далее цикл с `POLL_SECONDS = 1.5` до `HARD_STARTUP_SECONDS = 360` либо до дедлайна, который
  опубликовал Gateway (`startup_deadline`, `search.deadline`);
- «The model endpoint is never polled here».

Отсюда:

1. **Первый `ensure` в 10:21:32 — вероятнее всего именно из чата** (4 с после сообщения = сетевой
   round trip). Но это **не доказуемо**: в audit-записи нет поля `origin`. Дальнейшие два — фоновая
   авто-подписка с шагом 30 с (совпадает с `search_interval`).
2. **Turn не упал мгновенно.** Он ждал готовности и был ограничен ≤360 с. Строка `assistant` со
   статусом `error` и пустым содержимым — результат **обрыва клиента**, когда вы остановили команду:
   placeholder был создан в начале turn'а, а финальный статус проставился при разрыве потока.
   Поэтому «чат вернул error мгновенно» из прошлого отчёта — **моя неверная интерпретация**, снимаю.
3. `assistant=error` + 0 генераций + 0 Pod'ов согласуются с «модель так и не появилась, клиент ушёл».

### Требование §14 (origin) — то, чего не хватает, чтобы это доказать

Сейчас **невозможно** отличить ensure из чата от фонового повтора. Это и есть настоящий блокер
приёмки §5–§9. Нужно поле `origin` со значениями
`chat | manual_prewarm | background_retry | startup_auto_connect`:
в аудите Gateway, в ответе `ensure`, и в вызове клиента (`_gateway_ensure` уже несёт `operation_id`
и `task_id` — origin ложится рядом).

**Оценка: ~30–40 строк в двух приложениях + тест.** Это следующий шаг, и он дешёвый.

## C. ОПРОС `/v1/models` — КОРНЕВАЯ ПРИЧИНА НАЙДЕНА ТОЧНО

### Факт

`apps/backend/app/cloud/provider.py`, класс `GatewayProvider`:

```
READY_TTL_SECONDS = 8.0          # строка 70
async def health() -> bool:      # строка 80 — кэш на 8 с, затем новый probe
async def _probe_ready():        # строка 92
        payload = await self.client.models()      # → GET /v1/models
```

`client.models()` → `apps/backend/app/cloud/client.py:209` → `GET /v1/models`, timeout 15 с.

**`8.0` секунды ровно соответствует наблюдаемой частоте `409` каждые ~10 с** (8 с TTL + время ответа).

### Почему это дефект

Readiness-проба выполняется **независимо от того, существует ли compute-сессия вообще**. Пока AI
`Disconnected` и Pod'а нет, модель физически не может существовать, но клиент продолжает спрашивать
у Gateway список моделей — и получает `409` каждые 8 секунд, бесконечно (26 раз за 11 минут здесь).

Комментарий в самом коде требует обратного: «*readiness … must never perform a Gateway round trip*»
для `/health`; однако `_probe_ready()` делает именно round trip, и при отсутствии compute — заведомо
бесполезный.

### Предлагаемый фикс (§15)

`GatewayProvider.health()` должен **отвечать из известного состояния compute, не спрашивая модель**,
когда сессии/готовой модели быть не может:

```
MODEL_BEARING_STATES = {"ready", "generating"}

async def health(self) -> bool:
    if self._compute_state() not in MODEL_BEARING_STATES:
        # Спрашивать список моделей, которых не может быть, — это и есть 409 каждые 8 с.
        self._ready_value = False
        self._ready_at = time.monotonic()
        return False
    ... # существующий кэшированный probe
```

Проводка: `main.py:82` создаёт `GatewayProvider(settings, cloud.client)`, рядом доступен
`application.state.compute`; провайдер получает колбэк состояния. **~15 строк + тест.**

Порядок из §15 («chat → ensure → готовность → и только потом `/v1/models` → генерация») при этом
соблюдается по построению: `/llm/status` перестаёт быть источником бесполезных проб.

## E. ПРЕДЛАГАЕМЫЕ МУЛЬТИ-DATACENTER PLACEMENTS — ТРЕБУЕТ ВАШЕГО РЕШЕНИЯ

Реализация §6/§7/§9/§10/§11 — это отдельная работа (не сделана), но дизайн опирается на **уже
существующий** механизм, а не на новый:

- `Placement = (datacenter, volume_id, community_capable)` — уже есть в `candidates.py`.
- `RUNPOD_DATACENTERS="DC:VOLUME"` — **уже** парсится и **уже** добавляет placements; Volume
  указан в самом синтаксисе, то есть каждый placement обязан нести **свой** Volume.
- Порядок обхода уже: tier → самый дешёвый совместимый → датацентр самого Volume → добавленные.

Значит §9 (реестр placements) и §10 (порядок размещения) — это **не новый движок**, а:
1. конфигурация `RUNPOD_DATACENTERS` с реальными парами `DC:VOLUME` (**конфигурация, не хардкод в
   исходниках** — §9 соблюдён);
2. метаданные реплики на placement + отказ выбирать placement с неполной/устаревшей репликой (§8);
3. `origin` в аудите (§14);
4. политика BALANCED (§11) поверх существующего упорядочивания.

**Каких datacenter выбрать — я не выдумываю.** Их надо получить из провайдера: список DC, где
вообще доступны нужные карты, и где можно создать Network Volume. У меня нет подтверждённых данных
о том, какие DC это позволяют, поэтому в отчёте их нет. Это первый шаг следующей задачи.
