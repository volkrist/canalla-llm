# 2. ДОКАЗАТЕЛЬСТВА: ЖИВОЙ REST v2 (главный источник)

Схема скачана заново (не из кэша, не через наш клиент):

```
GET https://api.runpod.io/v2/openapi.json
→ HTTP 200, 255 104 байта
→ {"openapi": "3.1.0", "info": {"title": "Runpod REST API", "version": "2.0.0"}}
→ servers: https://api.runpod.io ; security: bearerAuth
→ paths: 38 ; schemas: 146
```

Пути, относящиеся к хранилищу и шаблонам (полный список, без сокращений):

| Путь | Методы |
|---|---|
| `/v2/network-volumes` | `get`, `post` |
| `/v2/network-volumes/{id}` | `delete`, `get`, `patch` |
| `/v2/billing/network-volumes` | `get` |
| `/v2/templates` | `get`, `post` |
| `/v2/templates/{id}` | `delete`, `get`, `patch` |
| `/v2/catalog/templates` | `get` |

Поиск по всему документу (включая описания и примеры):

| Слово | Вхождений |
|---|---|
| `globalvolume` | **0** |
| `global-volume` | **0** |
| `storagevolume` | **0** |
| `storage_volume` | **0** |
| `networkvolume` | 69 |
| `global` | 33 — **все** это `globalNetworking` (приватная сеть Pod↔Pod), не хранилище |

Схемы монтирования (то, чем Pod физически может обзавестись):

* **`Mounts`**: ровно два поля — `persistent` и `network`; «at-most-one of `persistent` or `network`»,
  `maxItems: 1` у `network`, вид монтирования **фиксируется при создании** (PATCH, вводящий новый вид,
  отклоняется с 400), `volumeId` неизменяем.
* **`PersistentMount`**: host-local, «**Deprecated**», «data does not survive a host failure»,
  «**Disallowed on CPU pods**».
* **`NetworkMount.volumeId`**: «ID of an existing **NetworkVolume in the same data center as the pod**».
* **`VolumeType`**: enum ровно из двух значений — **`STANDARD`, `HIGH_PERFORMANCE`** (значения
  `GLOBAL` нет).

Тело создания Pod (`CreatePodRequest`, все поля):
`cloud, cpu, dataCenterIds, globalNetworking, gpu, mounts, name, startJupyter, startSsh, templateId`.
**Хранилище — только `mounts`**, третьего вида нет.

Тело создания Network Volume (`POST /v2/network-volumes`), пример из живой схемы:
`{"name": "training-dataset", "dataCenter": "US-KS-2", "size": 50, "type": "HIGH_PERFORMANCE"}` —
то есть контракт умеет создавать **только региональный** том (у него обязателен датацентр).

Ресурс `Pod` (ответ `GET /v2/pods`) **открывает** `mounts` (поля: `actions, cloud, cluster, cost, cpu,
createdAt, cudaVersion, dataCenterId, globalNetworking, gpu, id, locked, mounts, name, runtime, ssh,
startedAt, status, template`). Но та же схема `Mounts` описывает только `persistent`/`network` и
запрещает лишние свойства (`additionalProperties: false`) — то есть **как публичный API отобразил бы
глобальное монтирование, контрактом не определено** (проверяемо только на реальном томе, которого нет).

# 5. ДОКАЗАТЕЛЬСТВА: путь через шаблон (§4 задания) — закрыт контрактом

Живая схема, дословная цитата `TemplateMounts`:

> «Storage mounts attached to a template. Templates support only a **single persistent mount** today;
> **any `network` property is rejected with 422** by the schema validator.»

Это значит: шаблон не может нести **сетевой** том (то есть и региональный, и тем более глобальный).
Сценарий задания «создать шаблон с подключённым Global Volume → создать Pod с `templateId` → получить
том автоматически» **невозможен на уровне схемы**, ещё до вопроса о типе тома. Плюс `Pod.template`
существует как ссылка, но воспроизводит только конфигурацию контейнера и persistent-том.

# 6. ДОКАЗАТЕЛЬСТВА: создание через консоль и цена

Документация прямо описывает **только консольный** путь создания: Storage → **+ New volume** →
Storage type = **Global volume** → имя → Create. Про API создания там нет ни слова, и это
подтверждено живой схемой (§2). Про миграцию сказано: «There is no in-console conversion tool.
Migration must be done manually», через `rsync --archive /workspace/ /workspace-global/`.

**Цена хранения Global Volume не опубликована.** Живая таблица тарифов на хранение:

| Тариф | Цена | Период |
|---|---|---|
| Volume disk (работающие Pod'ы) | $0.10/GB/месяц | посекундно |
| Volume disk (остановленные Pod'ы) | $0.20/GB/месяц | посекундно |
| **Network volumes (до 1 ТБ)** | **$0.07/GB/месяц** | ежечасно |
| Network volumes (свыше 1 ТБ) | $0.05/GB/месяц | ежечасно |

Строки для Global Volume **нет**. Страница Global Volumes даёт только цену **запросов** (Class A —
запись/листинг/создание: $0.005 за 1 000; Class B — чтение/метаданные: $0.0005 за 1 000) и говорит,
что хранение тарифицируется **отдельно**. Страница high-performance storage за ценой отправляет в
консоль: «Exact pricing varies by data center. Check the volume creation flow in the console for
current rates.» Поэтому условие §6 «цена явно доступна и разумна» — **не выполнено** (для хранения).

Прочие факты Global Volume из живой документации, важные для решения: бета; монтируется в
`/workspace`, а при наличии ещё и сетевого тома — в `/workspace-global`; максимум один глобальный +
один сетевой том на Pod; объектный бэкенд, «**not a fully POSIX compliant file system**»: нет файловых
блокировок, atomic rename, hard links, permission bits; eventual consistency; одновременная запись из
двух Pod не поддерживается; при балансе $0 том помечается и удаляется через 15 дней.

# 7. §6 / §7 / §8 — почему том не создан, модель не перенесена, старый том сохранён

* **§6 (создать один Global Volume)** — не выполнено по двум независимым причинам: (1) программного
  пути создания нет (§2), консольного сеанса у меня нет, а браузерная автоматизация консоли по §5
  недопустима; (2) цена хранения не опубликована, то есть предусловие «цена ясно доступна» не
  выполнено.
* **§7 (перенос модели)** — не выполнено, потому что переносить некуда. План остаётся готовым: один
  недорогой Pod с **двумя** томами (не-GPU), `/workspace` = региональный, `/workspace-global` =
  глобальный, затем `rsync --archive --verbose --human-readable`. Перед копированием фиксируются:
  точный путь GGUF, его размер, `sha256sum`, список обязательных файлов runtime
  (`/workspace/start-llm.sh`, `/workspace/check-llm.sh`); после — сверка SHA256 и байтов. Логи/кэш
  (`/tmp/alex-llm-*.log`, `.lock`) не копируются: они вне тома по построению.
* **§8 (не удалять `uwgeaie5b0`)** — соблюдено: том на месте, правило «удалять только после четырёх
  PASS (том проверен + llama.cpp грузит модель + путь автоматизации доказан + одна живая генерация)»
  в силе.

# 8. §9 — llama.cpp и объектное хранилище: НЕ проверено, и это честный статус

Тестировать нечего: тома нет. Что известно и что остаётся риском:

* штатный путь runtime — `exec` `/workspace/start-llm.sh`, который поднимает llama.cpp на
  `/workspace/models/orcarouter-qwen38/…Q5_K_M.gguf`; наш собственный `flock`
  (`/tmp/alex-llm-runtime.lock`) от семантик тома **не зависит** (он в `/tmp`);
* llama.cpp по умолчанию читает GGUF через `mmap`, а глобальный том — объектный, без гарантий
  POSIX (блокировки/atomic rename/hard links/permission bits), с eventual consistency;
* **ничто не утверждает, что `mmap` не работает**; утверждается, что гарантии нет. Поэтому статус:
  `mmap` = **UNKNOWN**, прямой монтаж = **UNTESTED**, и до живого теста план Б (сначала `--no-mmap`,
  затем разовая выкладка GGUF на быстрый локальный диск Pod'а) остаётся обязательным вариантом.
  Создавать GPU-Pod только ради этого сравнения в этом шаге было запрещено (§9/§18).

# 9. §10 / §11 / §12 — что уже готово в коде (и почему это не «сделано живьём»)

Абстракция, введённая в `1d02d84`, ровно под этот сценарий:

* `Placement.storage_type` ∈ `{regional_network_volume, global_volume}`;
* **региональный** том закрепляет ДЦ (модель лежит на томе в одном ДЦ);
* **глобальный** — не закрепляет: кандидаты строятся по **всем** ДЦ, которые сам каталог считает
  доступными, объявленный «домашний» идёт первым; неизвестный вид ведёт себя как закреплённый
  (fail closed);
* порядок `BALANCED` при одном логическом placement перестаёт «предпочитать ДЦ из-за хранилища» —
  так как позиция placement у всех кандидатов одинакова, решают доступность (фильтр + сток) и цена;
  `FASTEST`/`CHEAPEST`/`MANUAL` сохранены, потолок пользователя `$2.00/ч` не тронут;
* правила «ровно один Pod», single-flight и общий бюджет **60 секунд на все ДЦ** не менялись;
* есть гейт реплик (`replica_refusals`), но при **одном** глобальном томе он не нужен как механизм
  копий — нужен как валидация **единственного канонического объекта** (модель/её хэш/версия runtime),
  что схема записи уже умеет.

Статус: **PASS в политике и тестах, NOT RUN живьём** — живьём это включится одним значением
(`storage_type`) в тот день, когда провайдер откроет подключение.

# 10. §13 / §14 — почему живых тестов не было

* §13 (живая аллокация из чата с глобальным томом): нет пути подключения, поэтому аллокация физически
  не смогла бы приложить том; плюс в прошлом шаге живая ёмкость GPU была внешне заблокирована
  (`price_limit`, 0 совместимых доступных карт под потолком).
* §14 (живой Tor на том же Pod'е): того же Pod'а не существует.
* Живые Tor-доказательства предыдущих шагов (wire-level маршрутизация, SOCKS5h, доказательство цепи)
  сохранены отдельно и **не** выдаются здесь за новый живой тест.

# 12. §16 — почему это «BLOCKED», а не «не получилось»

Все требуемые условия проверены и подтверждены фактами:

| Условие §16 | Подтверждение |
|---|---|
| В живом REST v2 нет поддержки Global Volume | **ПОДТВЕРЖДЕНО**: 38 путей, 0 маркеров `globalvolume`/`storagevolume`, `VolumeType` без `GLOBAL`, в `Mounts` два вида |

# 15. ОДИН ДЕШЁВЫЙ ТЕСТ, КОТОРЫЙ МОЖЕТ РАЗБЛОКИРОВАТЬ (совместим с §5)

Единственная недоказанная возможность: живая реализация принимает **глобальный** id в
**документированном** поле `mounts.network.volumeId`, хотя описание поля говорит «NetworkVolume в том
же датацентре». Это проверяется **публичным** REST-вызовом — без приватных эндпоинтов, без браузера,
без ключей в отчёте.

1. **Вы** создаёте один Global Volume в своей консоли (Storage → + New volume → Global volume). Там же,
   до подтверждения, консоль покажет **цену** — то, чего нет в документации.
2. Вы сообщаете мне его **ID** (ID секретом не является).
3. Я делаю **один** ограниченный вызов: `POST /v2/pods` с
   `mounts.network = [{volumeId: <ID>, path: "/workspace"}]` и смотрю ответ:
   * **принят** → автоматизация существует через документированный API. Дальше: перенос модели
     (`rsync`), замеры загрузки и `mmap`, затем включение `storage_type=global_volume` (одно значение,
     код уже готов), затем живой тест §13 и Tor §14, и только потом решение об удалении старого тома;
   * **отказан (400/404/422)** → вопрос закрыт окончательно, остаёмся на одном региональном томе
     ($3.50/мес) до появления поддержки в API.

До этого шага правильная позиция — **ничего не менять**.
