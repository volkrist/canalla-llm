## GLOBAL VOLUME (проверено по собственной документации провайдера)

| Вопрос | Ответ |
|---|---|
| Доступен аккаунту | **Ресурса в API нет.** API v2 перечисляет storage-эндпоинты **только для network volumes** (list/create/get/update/delete). Создание документировано как консольный путь (Storage → New volume → Global volume). |
| Поддержан API | **НЕТ** — и для создания, и для подключения (см. следующую строку). |
| Можно ли создать Pod с ним | **НЕТ.** Схема create-pod в API v2: `mounts` = `persistent` **XOR** `network`; `mounts.network` — массив с **`maxItems: 1`**; `NetworkMount.volumeId` определён как *«ID существующего **NetworkVolume в том же датацентре, что и pod**»*. | Бета | **ДА** («Global volumes are in beta. Features and behavior may change before general availability.») |
| Точка монтирования | `/workspace` по умолчанию; `/workspace-global`, когда на том же Pod есть network volume. Максимум один global + один network том на Pod. |
| Монтируется между датацентрами | **ДА** — это его назначение («region-independent… any Pod, anywhere, can mount it at startup»). |
| Цена хранения | **unknown** — документация даёт цену *запросов* (Class A запись/листинг $0.005 за 1 000, Class B чтение/метаданные $0.0005 за 1 000) и прямо пишет, что «storage and request operations [are charged] separately», но цифры $/GB-месяц для глобального тома на прочитанных страницах **нет**. |
| Совместимость с llama.cpp при прямом чтении | **UNKNOWN** и не может считаться данной |
| Проблема с mmap | Документация прямо говорит, что это «object-backed storage, **not a fully POSIX compliant file system**»: **нет файловых блокировок, нет atomic rename, нет hard links, нет permission bits, eventual consistency**, и один глобальный том нельзя безопасно писать нескольким Pod одновременно. Штатный путь llama.cpp — `mmap` GGUF, то есть ровно те POSIX-семантики, которые сняты с гарантии. Ничто здесь не утверждает, что mmap *не работает*; здесь утверждается, что гарантии нет, а значит до живого теста продукт не может на это опираться. |
| Миграция с network volume | Поддержана, но **вручную**: подключить оба к одному Pod и `rsync --archive /workspace/ /workspace-global/`; «there is no in-console conversion tool». |
| Наш собственный лок | **не затронут ни в одну сторону**: runtime берёт свой `flock` в `/tmp`, а не на томе. |

### Также проверено, потому что это решает дизайн мульти-DC

* `dataCenterIds` — **«Preferred data centers for placement. Omit or pass an empty array to let the
  scheduler choose.»** Это список, и планировщик вправе выбрать. (Сейчас Canalla отправляет ровно
  один — что верно, пока модель лежит на одном региональном томе.)
* `mounts.network` `maxItems: 1` — **один network volume на Pod**, поэтому один Pod не может держать
  одновременно первичную и вторичную копию.
* **CPU Pod'ы поддерживают network volumes** («CPU pods support container disk and network volumes
  only») — значит реплику можно подготовить, **не покупая ни одной GPU-секунды**.
* **S3-совместимый API** для network volumes существует, эндпоинт у каждого датацентра свой, список
  из 15 ДЦ: `EU-CZ-1, EU-RO-1, EUR-IS-1, EUR-NO-1, US-CA-2, US-GA-2, US-IL-1, US-KS-2, US-MD-1,
  US-MO-1, US-MO-2, US-NC-1, US-NC-2, US-NE-1, US-WA-1`. **`US-TX-3` в список не входит**, поэтому
  байты первичного тома через S3 не прочитать — рабочий путь из `US-TX-3` это `rsync` Pod↔Pod.
  (`aws s3 sync` поддержан ограниченно; для большого одного объекта нужен длинный
  `--cli-read-timeout`.)

## OPTIONS

### A. Два региональных Network Volume — `US-TX-3` + один резервный ДЦ

* **Цена в месяц:** второй том. При тех же 50 GB STANDARD: 50 × $0.07 = **+$3.50/месяц**, всего
  **$7.00/месяц** за оба.
* **Плюсы:** единственная топология, которую **API провайдера умеет подключать**; чтение в каждом
  датацентре без объектных семантик; один Pod, одно монтирование — ровно та форма, которую продукт
  уже создаёт; placement однозначен, поэтому «на каком томе обязана лежать модель» остаётся одним
  фактом; `dataCenterIds` у каждого кандидата это уже несёт.
* **Минусы:** модель существует дважды, то есть возможна устаревшая копия — снимается записью
  реплики и путём отказа (реализовано, см. ниже); нужна одна копия на каждый добавленный датацентр.
* **Отказы:** отсутствующая/устаревшая запись отклоняет этот placement (он больше не может молча
  отдать не те веса); потеря первичного тома не оставляет продукт без резерва.
* **llama.cpp:** без изменений — это то, на чём продакшен уже работает.

### B. Один Global Volume, модель читается прямо из `/workspace-global`

* **Цена в месяц:** **unknown** (в прочитанной документации нет $/GB-месяц) **плюс** плата за каждый
  запрос чтения.
* **Плюсы:** одна копия весов на все датацентры; датацентр становится свободным параметром.
* **Минусы:** **не реализуемо продуктом** — нет пути подключения через API (см. выше). Потребовало бы
  разворачивать каждый Pod руками из консоли, что уничтожает автоматический жизненный цикл, ради
  которого выпускается 1.2.0. Сверху: бета, объектное хранилище со снятыми POSIX-гарантиями,
  неизвестное поведение mmap, отсутствующая цифра цены и удаление тома через 15 дней при балансе $0.
* **Отказы:** один и тот же файл нельзя безопасно писать из двух Pod; изменения после монтирования
  могут быть не видны; плохой путь чтения проваливается **на загрузке модели**, то есть после начала
  списания денег.

### C. Global Volume как канонический том + локальная подготовка в каждом Pod

* **Цена в месяц:** как B, плюс container disk, вмещающий вторую копию весов.
* **Холодный старт:** полное копирование модели с объектного тома в контейнер **на каждом** холодном
  старте. Байты неизвестны (§16), но объём передачи того же порядка, что сама модель — десятки минут,
  а не секунды, для ~20 GB GGUF на скоростях объектного чтения, и платится это **каждый** холодный
  старт (а idle-политика останавливает Pod через 10 минут, то есть холодные старты часты).
* **Плюсы:** медленное каноническое хранилище отделено от быстрого локального чтения.
* **Минусы:** **тоже не реализуемо** (то же отсутствие пути в API, та же бета) и добавляет самый
  медленный холодный старт ровно на тот путь, которого ждёт пользователь. Его единственное реальное
  преимущество перед A — независимость от региона — всё равно недоступно.

### Что для этого сделано (закоммичено, `1d02d84`)

* `Placement.storage_type` ∈ `{regional_network_volume, global_volume}`. Региональный том
  **закрепляет** датацентр; глобальный — **нет**: тогда кандидат строится в каждом датацентре,
  который сам каталог считает доступным, а объявленный «домашний» идёт первым. Неизвестный вид
  хранилища ведёт себя как закреплённый (fail closed).
* `candidates.build_plan(..., replica_refusals=...)` пропускает placement, копия модели на котором
  не доказуемо является этой моделью, и записывает причину в аудит плана
  (`allocation.plan.replica_refusals`) даже когда был использован другой placement.
* `app/compute/replicas.py`: вердикты `missing / partial / unverified / wrong_model / wrong_hash /
  wrong_runtime`, ключ — id тома; план, опустевший из-за них, завершается `replica_not_ready`, а не
  обвинением ёмкости. **Добавленный** placement обязан нести проверенную запись; placement, на
  котором продакшен уже работает, файлом, которого у него никогда не было, не блокируется — а запись,
  которая **есть**, уважается всегда. Ожидание, которое развёртывание не может сформулировать, — это
  молчание: оно никогда не противоречит записи, которая значение называет.

## RECOMMENDATION

**A — два региональных Network Volume.** Не как предпочтение: B и C — единственные альтернативы,
убирающие копию на каждый датацентр, и обе **вне API провайдера** для продукта, который создаёт Pod'ы
программно. A — та топология, которую API умеет подключить, та, с которой llama.cpp уже читает в
продакшене, и та, у которой цена опубликована ($0.07/GB-месяц). Лишняя копия — *доказуемый* риск, и
механизм отказа от неё теперь есть; риски B (бета-семантики, неизвестный mmap, нет цены, нет API)
сегодня недоказуемы.

Резервный датацентр, предварительно и с явным условием: **`US-KS-2`** — американский ДЦ (тот же
регион комплаенса и класс задержки, что `US-TX-3`), присутствует в S3-списке провайдера, поэтому
любая будущая репликация дёшева, и того же размера/класса, что первичный. **Он должен быть
подтверждён одним read-only чтением каталога до создания тома**: выбор обязан опираться на то, где
карта ≥48 GB реально доступна под $2.00/ч, а эти данные читаются живьём, а не угадываются. Том не
создан, поэтому при другом ответе ничего не потеряно.

* **Байты и SHA256 модели не измерены.** §16 просил точный размер реплики, прочитанный с первичного
  тома. Это чтение требует живого аккаунта и относится к шагу копирования, а не к шагу решения:
  копирование не должно начинаться без этих двух чисел, и схема записи реплики требует оба.
* **Цена Global Volume в $/GB не опубликована** на прочитанных страницах, поэтому месячная стоимость
  варианта B — **unknown**, а не выгодная: это ещё одна причина, по которой он не рекомендован.
* **Доступность по датацентрам не ранжирована** — это одно read-only чтение, и именно оно обязано
  решить выбор резервного ДЦ.
* **Прямое чтение GGUF с глобального тома через mmap не проверено** и, поскольку API не может
  подключить такой том, для этого релиза не требуется. Если провайдер позже откроет это через API,
  этому пути нужен один ограниченный живой тест до замены варианта A.
* **Прямой режим** (dev/private) не обращается к реестру реплик: он размещает одобренную карту
  оператора на его собственном томе, где реестр добавил бы режим отказа, ничего не защищая. Второй
  placement может существовать только в shared-режиме.
