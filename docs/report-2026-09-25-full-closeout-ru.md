## 2.2 `STEP 5B FINAL FIX + RC CLOSEOUT` (Finding A и Finding B)

**Finding A (ложный/устаревший `searching` и бесконечный «Connecting») — ИСПРАВЛЕН.**

Источником правды стала не надпись в интерфейсе, а состояние операции:

* переход (`searching`) законен только при **реальной** операции: есть `operation_id`, есть
  `started_at`, дедлайн не истёк;
* истёкший или безличный поиск **сворачивается** в `offline` с типизированной причиной
  (`collect_expired_search` в `tick` и та же производная в `status_payload` — то есть чтение до
  следующего тика тоже честное);
* `COMPUTE_SEARCH_TIMEOUT_SECONDS` — **серверный и жёстко ограничен 60 секундами**, клиент не может
  его расширить;
* фронтенд получил защитную обработку устаревшего снимка, но **не** изобретает жизненный цикл.

**Finding B (обычный чат обязан сам запросить compute) — ИСПРАВЛЕН.**

* `app/cloud/demand.py` — один жизненный цикл (`SharedDemand`) с single-flight: логический эквивалент
  `POST /compute/ensure` выполняет **оркестратор**, а не «нажатие» в UI;
* кнопка «Запустить AI» осталась — теперь это **необязательный prewarm** того же жизненного цикла, и
  они дедуплицируются друг с другом;
* исходное сообщение остаётся в ожидании и исполняется **один раз**; при невозможности получить
  compute — типизированный отказ, без генерации и без второго Pod;
* измеренный эффект (предыдущий шаг): завершённый обход ёмкости закрывает ход — **937 с → 4.8 с**.

**Чего Finding A/B стоили:** «Connecting» больше не может висеть бесконечно; отсутствие операции
означает красный Disconnected с типизированной причиной.

## 2.4 `FINAL COMPUTE UX / MULTI-PLACEMENT FIX`

**Три корневые причины установлены точно, одна исправлена сразу.**

**UI-дефект (`0d29282`, принят):** панель **сама** подставляла `gpu_id: "NVIDIA L40S"`, пустое поле
показывало эту же строку как *placeholder* (выглядело как введённое значение), а переключение режима
не очищало закрепление; кнопка «Запустить AI» принудительно ставила `auto_connect: true`, и только
backend отказывал в состоянии «вручную + пусто» (`app/compute/schemas.py:39`). Теперь:

* автоматический режим: `gpu_id = null`, поля точной карты **нет**, имени GPU в форме нет вообще, нет
  красной ошибки;
* ручной режим: карта выбирается **из живого каталога**, без свободного ввода;
* правила вынесены в `apps/desktop/src/lib/compute-policy.ts` и покрыты тестами.

**Живой shared-чат:** доказано, что три вызова `POST /compute/ensure` с интервалом ~30 с — это
собственные ограниченные ретраи `SharedDemand._attempt` внутри 60-секундного окна, а **не** фоновый
цикл (в shared-режиме фоновый повтор отключён). Первый вызов был через ~4 с после сообщения — то есть,
вероятно, чат; теперь это **читается полем**: `origin`.

**Ограничение размещения:** `RUNPOD_DATACENTERS` пуст → фактически **один** placement (`US-TX-3`).
Это и есть главная причина, по которой «Ищем GPU» мог длиться час: один слот, одна физическая точка.
Исправление — не в UI, а в аллокаторе (см. 2.6).

## 2.6 `FINAL STORAGE / MULTI-DATACENTER DECISION` (этот шаг)

Полный текст: `docs/report-2026-09-25-storage-multi-datacenter-decision.md`
(и копия на рабочем столе: `CANALLA-LLM-STORAGE-MULTI-DC-ОТЧЁТ.md`, побайтово равна коммиту).

### A. Бесплатные фиксы — сделаны

1. **Гейт `/v1/models` (`0867af0`).** `GatewayProvider.health()` раньше обновлял проверку готовности по
   TTL независимо от того, есть ли вообще compute: отключённый ИИ спрашивал у Gateway список моделей,
   которого не могло быть, и получал **409 каждые ~8 секунд** (26 раз за 11 минут в живой приёмке).
   Теперь, когда снимок compute сам доказывает, что модели быть не может (нет сессии, завершённый
   отказ ёмкости, остановленный Pod, ошибка провайдера), ответ берётся **из состояния, без запроса**.
   Проверка осталась для всех model-bearing состояний и для «ещё не читали» — «не смотрел» ≠ «не
   готово». Набор состояний записан явно, и тест удерживает его равным
   `READY_STATES | STARTING_STATES`.

2. **Четыре стратегии (`041f842`).** Пользователь выбирает **порядок** кандидатов, а не то, что можно
   бронировать:

   | Значение | Порядок |
   |---|---|
   | **balanced** (по умолчанию) | tier → порядок placement'ов → **самая дешёвая карта, доступная прямо сейчас** → лучший сток → id |
   | **fastest** | tier → лучший сток → placement → цена |
   | **cheapest** | tier → цена по всем placement → placement → id (**исторический порядок**) |
   | **manual** | тот же порядок, что balanced, по закреплённой карте |

   Доступность — **фильтр**, а не тайбрейк: карта без стока в датацентре кандидатом там не является.
   Поэтому «не ждать дешёвое железо» выполняется, и при этом ни одна стратегия не покупает карту
   дороже, чем доступная в том же placement. Матрица **4 стратегии × 3 типизированных отказа**
   (потолок цены / порог VRAM / нет стока) это фиксирует.
   `manual` — закрепление под другим именем: без карты Gateway отказывает
   (`compute_policy_invalid`), а не сортирует по умолчанию; неизвестное значение отклоняется как
   некорректное, а не подменяется молча.

   **Важное:** найдена реальная ошибка проводки — маршрут `/compute/ensure` собирал `caps` по полям
   вручную и **терял** `strategy`; без этого «fastest» молча стал бы balanced. Исправлено.

   **Единственное изменение поведения:** установка, которая стратегию не выбирала, теперь идёт по
   balanced вместо cheapest. Различаются они ровно тогда, когда более дешёвая карта есть **только во
   втором** placement — там balanced сохраняет датацентр с моделью. При одном placement обходы
   совпадают, поэтому **все** прежние тесты аллокации прошли без изменений. Потолок оператора $2.00
   не тронут и не заменён константой.

3. **Виды хранилища и реплики (`1d02d84`).**

   `Placement.storage_type` ∈ `{regional_network_volume, global_volume}`:

   * региональный том **закрепляет** датацентр (модель лежит на томе, который в одном ДЦ);
   * глобальный — **нет**: кандидаты строятся в каждом датацентре, который **сам каталог** считает
     доступным, объявленный «домашний» первым. Это и есть автоматическое обнаружение ёмкости по ДЦ
     из данных провайдера, без ручных списков;
   * неизвестный вид хранилища ведёт себя как закреплённый (fail closed).

   `app/compute/replicas.py` — вердикты `missing / partial / unverified / wrong_model / wrong_hash /
   wrong_runtime`, ключ — id тома. `build_plan(replica_refusals=...)` пропускает placement, копия
   модели на котором не доказуемо является этой моделью, и **записывает причину в аудит**
   (`allocation.plan.replica_refusals`) даже когда использован другой placement. План, опустевший
   из-за них, завершается `replica_not_ready`, а не «нет ёмкости». **Добавленный** placement обязан
   нести проверенную запись; placement, на котором продакшен уже работает, файлом, которого у него
   никогда не было, не блокируется; запись, которая есть, уважается всегда. Ожидание, которое
   развёртывание не может сформулировать, — молчание: оно не противоречит записи.

### B. Global Volumes — вопрос закрыт фактами API, а не мнением

Прочитано в живой документации и API-референсе провайдера (25.09.2026):

* **создание глобального тома — консольный путь**; в API v2 storage-эндпоинты есть **только для
  network volumes**;
* **подключить глобальный том к Pod через API нельзя**: схема create-pod допускает `mounts.persistent`
  **XOR** `mounts.network`, у `mounts.network` **`maxItems: 1`**, а `NetworkMount.volumeId` определён
  как «NetworkVolume **в том же датацентре, что и pod**»; поля глобального тома в схеме **нет вообще**;
* вид монтирования **фиксируется при создании** (PATCH с новым видом → 400), то есть подключить и
  постфактум нельзя;
* том **в бете**, объектный, «**not a fully POSIX compliant file system**»: нет файловых блокировок,
  atomic rename, hard links, permission bits; eventual consistency; одновременная запись из двух Pod
  не поддерживается;
* цена: объявлена цена **запросов** ($0.005/1 000 записей, $0.0005/1 000 чтений) и прямо сказано, что
  хранение тарифицируется **отдельно** — но цифры `$/GB-месяц` для глобального тома в документации
  **нет**: цена = **unknown**;
* монтируется в `/workspace`, при наличии ещё и network volume — в `/workspace-global`; максимум один
  глобальный + один сетевой том на Pod;
* миграция с сетевого тома — **вручную** `rsync`, «in-console conversion tool» отсутствует.

**Вывод:** варианты B (один глобальный том, прямое чтение) и C (глобальный том + локальная подготовка)
**не реализуемы продуктом**, который создаёт Pod'ы программно. Их единственное преимущество —
отсутствие копии на каждый датацентр — недоступно, а риски (бета, снятые POSIX-гарантии, неизвестное
поведение `mmap`, отсутствие цены) сегодня недоказуемы.

**Рекомендация — A: два региональных Network Volume.** Это единственная топология, которую API умеет
подключить, та, с которой llama.cpp уже читает в продакшене, и та, у которой цена опубликована:
**$0.07/GB-месяц** (до 1 ТБ).

Дополнительно проверено и учтено: `dataCenterIds` — это **«preferred data centers… omit or pass an
empty array to let the scheduler choose»**; CPU Pod'ы **поддерживают network volumes** (реплику можно
подготовить без GPU-секунды); S3-совместимый API есть у 15 ДЦ
(`EU-CZ-1, EU-RO-1, EUR-IS-1, EUR-NO-1, US-CA-2, US-GA-2, US-IL-1, US-KS-2, US-MD-1, US-MO-1,
US-MO-2, US-NC-1, US-NC-2, US-NE-1, US-WA-1`), и **`US-TX-3` в этот список не входит** — поэтому
рабочий путь копии из `US-TX-3` это `rsync` Pod↔Pod.

**Резервный ДЦ (предварительно, с условием): `US-KS-2`** — американский ДЦ того же класса, есть в
S3-списке. **Обязательное условие: подтвердить одним read-only чтением каталога** (где реально
доступна карта ≥48 GB под $2.00/ч) **до** создания тома. Том не создан, поэтому при другом ответе
ничего не потеряно.
