# ЧТО ПРОИЗОШЛО ДОСЛОВНО (две попытки, обе корректно завершились отказом)

### Попытка 1 — отклонён **мой** payload, а не ID

```
HTTP 422 Unprocessable Entity
{"detail": "Request validation failed.", "errors": ["$.args: got object, want string"], "status": 422}
```

Валидатор не принял **документированную объектную форму** поля `args`
(`{"entrypoint": [...], "cmd": [...]}`), хотя именно так она описана в живой схеме. Это отказ по форме
**моего** запроса, он ничего не говорит о глобальном томе, и Pod не создавался (`pods_after: []`).
Исправление: команда перенесена в два поля, которые в той же схеме объявлены массивами —
`entrypoint` + `cmd` (они описывают ровно одну команду, как и требует контракт).

### Попытка 2 — отклонён **ID**, форма запроса принята

```
{"name": "canalla-gv-test1-…", "cloud": "SECURE", "image": "alpine:3.20", "disk": 10,
 "cpu": {"id": "cpu3c", "vcpuCount": 2},
 "mounts": {"network": [{"volumeId": "cmugq2bsv000007js3sa47w6j", "path": "/workspace"}]},
 "entrypoint": ["/bin/sh", "-c"], "cmd": ["set -x; … тестовый файл … sleep 300"],
 "dataCenterIds": ["US-TX-3"]}
```

→ **HTTP 400: `Network volume "cmugq2bsv000007js3sa47w6j" not found`**

Здесь важно, **почему** это доказывает именно отказ по ID, а не «сломанную форму запроса»: ошибка
возникла на шаге **разрешения тома** — то есть схему и обязательные поля валидатор уже пропустил
(иначе мы получили бы 422 с перечислением полей, как в попытке 1). Отказ пришёл ровно на
`mounts.network[].volumeId`, и сообщение называет этот ID.

# ПОЧЕМУ ЭТО НЕ МОЖЕТ БЫТЬ ОПЕЧАТКОЙ В ID

Три независимых свидетельства, и вместе они закрывают вопрос:

1. **Сообщение говорит «Network volume».** Эндпоинт искал ID среди сетевых томов. Глобальный том —
   другой тип ресурса (в консоли он помечен «Global», региональные — меткой датацентра).
2. **API v2 вообще не умеет адресовать глобальный том:** в живом OpenAPI нет ни одного пути, схемы,
   поля или значения enum для него (`globalvolume` = 0, `storagevolume` = 0, `VolumeType` =
   `STANDARD | HIGH_PERFORMANCE`), а `mounts` содержит только `persistent` и `network`.
3. **Аккаунт не показывает этот том ни одной публичной поверхности:** `GET /v2/network-volumes`
   возвращает **только** `uwgeaie5b0`; `GET /v2/billing/network-volumes` — `uniqueNetworkVolumeCount: 1`;
   `GET /v2/pods` — 0 Pod'ов; `GET /v1/network-volumes` — 400 (такого пути в v1 нет).

**Одна честная оговорка:** сообщение «not found» выглядело бы так же при опечатке в ID. По правилу
«если отклоняет ID → STOP» я **не** отправлял дополнительных запросов (ни с заведомо несуществующим
volume-id как контроль, ни со вторым ID), поэтому полной уверенности «ID набран верно» у меня нет.
Но на вывод это не влияет: даже с идеальным ID адресовать глобальный том публичным API нечем — пункты
2 и 3 не зависят от строки ID вообще. Если вы хотите исключить опечатку, пришлите ID заново — тест
занимает одну команду и стоит $0, пока провайдер отвечает отказом до создания Pod'а.

# ЧТО ИЗ ЭТОГО СЛЕДУЕТ ДЛЯ ПРОДУКТА

* **Архитектура «один Global Volume + автоподключение» сегодня не реализуема** — не из-за нашего
  клиента, а потому что у провайдера нет публичного способа подключить такой том к Pod'у. Любой
  рабочий путь сегодня — только консоль вручную, а это по §5 задания недопустимая производственная
  зависимость.
* **Второй региональный Network Volume НЕ создан** (и не будет создан автоматически).
* **`uwgeaie5b0` сохранён**; удалять его нечего и незачем — модель не копировалась.
* **Продукт менять не требуется**: политика уже умеет `storage_type = global_volume` без закрепления
  датацентра (коммит `1d02d84`, тесты зелёные). В тот день, когда провайдер откроет подключение в API,
  включение сведётся к одному значению + переносу модели.
* **Стоимость:** $0. Ни подов, ни томов, ни GPU.
